【两个坐标空间的对照（关键）】
  物理像素来自 Win32，DIP 来自 WPF。二者只在 100% 缩放且原点重合时才相等。

· \\.\DISPLAY1（主屏）
    物理像素：原点 (0,0)  尺寸 1920×1080
    对应 DIP：尺寸约 1536×864（按本屏 125 % 缩放）
    工作区：物理 (0,0 1920×1020)  →  DIP 约 1536×816
· \\.\DISPLAY2
    物理像素：原点 (-1920,0)  尺寸 1920×1080
    对应 DIP：尺寸约 1536×864（按本屏 125 % 缩放）
    工作区：物理 (-1920,0 1920×1020)  →  DIP 约 1536×816

【一致性检查】
主屏工作区宽度：物理换算 1536 DIP vs WPF 报告 1536 DIP（差 0）
✓ 换算基准与 WPF 一致，可以按显示器 DPI 做像素↔DIP 换算。
显示器数量：2，不同 DPI 档位：1
· 存在负坐标显示器（主屏左侧或上方）：定位计算必须支持负原点，不能假设从 0 开始。

  A = WPF 的 Left/Top（按目标屏 DPI 换算）；B = Win32 SetWindowPos（物理像素）。

【全屏检测】
  路径一：前台窗口矩形与所在显示器边界比较（GetWindowRect，并用 DWM 可见边框修正）。
  路径二：SHQueryUserNotificationState，即 Windows 判断「要不要弹通知」时用的那套。
  任务栏自动隐藏：否

  · 当前实际前台窗口
      前台窗口：?（进程 0）  类名 
      路径一：无法判定——当前没有前台窗口（会话正在切换，或已锁屏）。
        GetWindowRect = (0,0 0×0)
        DWM 可见边框 = （不可用）
        所在显示器 =  (0,0 0×0)
      路径二：Busy（全屏）
      两路一致：是；抑制触发：是

  · 查询耗时
      路径一（完整探测，含取类名/标题/进程名）：最小 0.00 微秒，中位 0.10 微秒，最大 0.40 微秒
      路径二（外壳调用）：最小 0.50 微秒，中位 0.60 微秒，最大 4.30 微秒
      廉价查询 IsFullscreenActive（只走路径一，不做描述性查询）：平均 0.97 微秒（200 次）
      → 外壳调用中位数为廉价查询的 0.6 倍（最大 4 微秒，且随状态波动）；因此触发路径只用路径一，外壳状态留给诊断与低频确认。
        另一条理由在下一段实测里：外壳那条路径看不到副屏上的全屏窗口。

  · 实测全屏窗口（无边框、置顶、铺满主屏；会短暂全屏显示，属预期）
      事件钩子：✓ 已安装（EVENT_SYSTEM_FOREGROUND + EVENT_OBJECT_LOCATIONCHANGE）
      探测窗口：句柄 0x470812，摆放结果 (0,0 1920×1080)（目标主屏 (0,0 1920×1080)）
      ⚠ 没能把探测窗口切到前台（当前前台是「?」）。
        **本次全屏检测的阳性用例未生效，以下三项标记为「未验证」，不计入失败。**
        它们只说明代码没有崩，不能作为检测正确性的证据。
        从脚本或后台启动时 Windows 会拒绝前台切换，属可预期的情形；
        要以人工方式复测，请在交互式会话里直接运行 --diagnose。
      排除自身时：路径一 = 无法判定（期望「已排除」），路径二 = Busy（全屏）
      ○ 未验证：自身窗口排除（需要探测窗口真正在前台）
      不排除自身时：路径一 = 无法判定（期望「全屏」），路径二 = Busy（全屏）
      ○ 未验证：路径一把铺满窗口判为全屏
      事件钩子收到判定变化：0 次
      ○ 未验证：事件钩子收到判定变化（窗口没能成为前台，本就不该有变化）
      排除自身的监视器收到变化：0 次（期望 0——自身窗口不该改变判定）
      —— 本次有 3 项未验证（详见上方「未生效」说明），失败计数不含它们。
      关闭后：路径一 无法判定，路径二 Busy，两路一致；结论：仍抑制触发

  · 已知边界（本机实测，完整数据见 tmp/fullscreen-probe 的输出）
      前提：进程必须声明 PerMonitorV2。缺清单时 GetWindowRect 返回虚拟坐标、DWM 可见边框
            返回物理像素，两者混用会让副屏全屏被误判成非全屏（实测过）。
      ✓ 无边框铺满主屏：两条路径一致判为全屏
      ✓ 无边框 + 最大化：两条路径一致判为全屏
      ✓ 普通窗口最大化：可见边框停在工作区（1368 < 1440），两条路径一致判为非全屏
      ✓ 带边框窗口被放大到整屏：GetWindowRect 恰好等于整屏，可见边框 (9,0 2542×1431) 小一圈，
        判为非全屏。DWM 可见边框的修正正是为这一条而加——只看 GetWindowRect 会误判成全屏。
      ✓ 同一窗口内切换全屏（F11 式，前台窗口不变）：靠位置变化事件，两次翻转都收到
      ✓ 全屏窗口最小化：判定立刻解除
      ✗ 副屏上的全屏窗口：路径一判为全屏，路径二漏检（报非全屏），两者不一致
      ✗ 后台有全屏窗口、前台是别的小窗口：不抑制。检测只看前台窗口，这是取舍
      ⚠ 任务栏自动隐藏时：最大化窗口与全屏在几何上无法区分，任何基于矩形的判定都分不开
      ⚠ 独占全屏（D3D）的游戏：本机无法造出，未实测；路径二有专门状态可识别
      ⚠ 路径二自身不稳定：实测耗时随状态在 1.9 微秒到 2.5 毫秒之间波动，且见过「非全屏窗口在前台却报 Busy」
